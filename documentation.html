Sofia MCP Server

Allow autonomous AI assistants to operate your Sofia creator marketing engine through the open Model Context Protocol.

Zero client installation required

Sofia hosts a live, high-throughput Model Context Protocol server. An AI model can discover creators, negotiate terms, sign contracts, review videos, and execute payouts directly through natural conversation — no custom HTTP integrations or glue code needed.

Live Remote Endpoint https://app.sofia.com/api/mcp

What Sofia exposes to your agent #

The Sofia MCP server maps 1:1 with Sofia’s battle-tested REST API, protected by granular OAuth 2.1 capability scopes. Every capability is exposed as a typed, structured MCP tool, alongside a foundational whoami tool for real-time verification of tenant identity, permission boundaries, and sub-account access.

Read-Only Safety

Read scopes reveal idempotent, query-only tools that cannot mutate account state or spend campaign capital.

State Guardrails

Write tools mutate Sofia state reversibly, carrying full confirmation guardrails in their schema descriptions.

Financial Safeguards

Sensitive operations (contract signing, wallet transfers, payout runs) enforce dry-run validations before execution.

The quick-pay claim link facility is directly accessible to agents via create_quickpay_claim_link.

Prerequisites & Security Architecture #

To connect an AI assistant, you need three components:

1

MCP-Enabled Client

Claude Code, Claude Desktop, Cursor, VS Code (Copilot/Cline), or any assistant speaking MCP over Streamable HTTP.

2

OAuth 2.1 Client

Sofia MCP uses standard OAuth 2.1 with Dynamic Client Registration (RFC 7591) to mint client IDs with no manual API key rotation.

3

Bearer Token (PKCE)

Authorized via PKCE (S256). Sofia tokens are multi-audience: the same credential validates for both REST API and MCP endpoints.

Zero-Configuration Discovery (RFC 9728): When an unauthorized client connects, Sofia returns an HTTP 401 with a WWW-Authenticate challenge containing protected-resource metadata. Compliant tools discover the authorization server dynamically, enabling complete zero-click setup from the URL alone.

Connect your assistant in 60 seconds #

claude mcp add --transport http sofia https://app.sofia.com/api/mcp

Claude Code will initiate the browser-based OAuth authentication flow automatically on its first execution.

Understanding Sofia Connectors:

Two distinct configurations use the term Connectors:

  • Incoming Assistant Connectors: Your client’s settings (such as Claude Desktop’s Settings → Connectors) point an external assistant into your Sofia brand workspace. This documentation covers this flow.
  • Outgoing Sofia Connectors: Inside the Sofia dashboard under Settings → Sofia Connectors, Sofia itself connects outward to third-party data providers and e-commerce platforms.

Role-Based Permission Ceilings: A user’s consented scope array acts as a strict ceiling. If a user later has their permissions adjusted by a workspace administrator, subsequent token refreshes narrow the accessible tool capabilities immediately, ensuring AI actions never bypass organizational roles.

Interacting with Sofia in natural language #

Once your client is connected, instruct your assistant to verify its active tenant context before initiating operations:

"Call whoami to confirm which Sofia workspace and permissions are currently connected." Verification

You can then command complex operations in plain language:

"List my active Sofia campaigns, show creator applicant counts, and draft offer terms for the top 3 candidates." Workflow

Every invocation is cryptographically bound to the authenticated workspace. Requesting actions beyond granted scopes yields an actionable reauthorization prompt rather than an ambiguous error.

Workspace Switching: Modifying the active workspace in the Sofia web browser does not automatically alter an established MCP session. To point your agent at another company, disconnect the client and authorize again with the desired workspace selected.

Agency Sub-Account Delegation #

Agencies managing multiple client brands on Sofia can grant their AI agents global or scoped sub-account access during OAuth consent.

  • The whoami response includes a subaccountAccess property: null (single workspace), "all" (entire client portfolio), or an explicit array of client workspace IDs.
  • All business tools support an optional act_as_subaccount_id parameter. Pass the client workspace ID (discovered via list_companies) to execute actions directly on that brand’s behalf.
  • Under the hood, Sofia routes the request with an X-Act-As-Company tenant header, rigorously verifying parent-child relationships and live permission ceilings on every call.

Intent-Driven Capability Discovery #

Because some AI client environments enforce strict limits on total tool schema size, Sofia implements a two-stage discovery pipeline. Core discovery tools are registered first so models never drop critical capabilities:

Step 1 · Semantic Search

Intent Resolution

The agent calls find_capability with an English description of the desired task to locate candidate tools.

Step 2 · Schema Inspection

On-Demand Schemas

The agent loads the exact JSON input schema via catalog_get_schema right before dispatching data.

Step 3 · Confirmation

Parameter Review

The agent presents resolved enum values, budget amounts, and parameters to the user for explicit confirmation.

Step 4 · Safe Execution

Gated Invocation

The agent dispatches via catalog_invoke_read, catalog_invoke_write, or catalog_invoke_sensitive.

Sofia Native Messaging Architecture #

Sofia operates its own high-concurrency native chat network. When interacting with creator conversation streams through MCP:

  • All channels, threads, and individual messages utilize RFC 4122 UUID identifiers.
  • Payload objects report chatType: "native", source: "native", and route responses over the native delivery lane.
  • During scheduled workspace database maintenance, tools return a graceful HTTP 409 Conflict with meta.reason: "messaging_migrating". Agents are instructed to pause and retry after 60 seconds.

Safety Engine & Idempotency #

Enforced strictly at the protocol kernel layer, not on the client:

Security Rule Kernel Behavior
Sandbox Isolation Sensitive tools (financial transfers or outbound communications) are rejected immediately when operating on sandbox or staging credentials.
Kill Switch (Safe Mode) The MCP_SAFE_MODE environment flag instantly deactivates all sensitive tools across the workspace without interrupting read queries.
Idempotency Locks All money-moving and contract actions require an Idempotency-Key header, ensuring network retries never trigger duplicate payouts.
Strict Tenant Binding Every call is locked to one verified company context, preventing cross-tenant data leakage.

Actionable Error Handling #

Sofia transforms raw HTTP status codes into self-healing instructions for the calling LLM:

Trigger Condition Protocol Response & Agent Recovery
Missing Scope Returns descriptive requires 'X:write' scope accompanied by the full cumulative OAuth challenge for the user to re-consent seamlessly.
Cross-Tenant ID Returns Not found or not visible to this Sofia workspace, preventing guesswork.
Sensitive Sandbox Call Returns Action performs real irreversible side-effects; disabled on sandbox token.
Safe Mode Active Returns Operation disabled: Sofia server running under MCP_SAFE_MODE.
Rate Throttled Returns Rate limit exceeded: back off and retry in N seconds with standard headers.
